# Spike: Claude Code and Codex over ACP (8 Oct 2026)

Run by Claude Opus 5.5 (Claude Code) on the Linux dev machine (Nobara, Node 22.22.2, installed `claude` 2.1.292 and `codex-cli` 0.160.1). Each point says whether it was **run** or only **read** (adapter source in `node_modules`, or docs). Driver, dummy MCP server and logs: `tmp-test/acp-spike/` (`scripts/acp_drive.py <scenario>`, `logs/<scenario>.jsonl`). Secrets in the kept logs are redacted.

## Verdict

- **Claude Code: works with caveats.** MCP per session, built-in tools off, streaming and Stop all verified. Caveats: user hooks, plugins and project settings still load, and the terms are unclear.
- **Codex: works with caveats, more of them.** MCP, read-only sandbox, edit gated by permission and streaming all verified. It needs its own bundled Codex, because the installed 0.160.1 broke `session/new`. The user's own MCP servers leaked into the session. A side thread for the title runs with the user's full access. `session/cancel` latency was not measured.
- **Gemini CLI:** desk only. `gemini --acp` in `@google/gemini-cli` 0.63.0 (npm, Apache-2.0, Node >=20) takes stdio `mcpServers` in `session/new`. Issue google-gemini/gemini-cli#29595 reports a permission prompt on the first call of every client-supplied MCP tool.

## What was run

The adapters were installed with `npm install --ignore-scripts` in `tmp-test/acp-spike/{claude,codex}` and spawned with a clean environment (HOME, PATH, LANG only). The session cwd was an empty `work-*` directory, and the MCP server was a stdio Python `echo` server named `spike`. Each agent got two prompts on the user's own login. Claude also got one prompt in an empty `CLAUDE_CONFIG_DIR` that holds no credentials. The `-missing`, `-loggedout` and probe scenarios sent no other prompts.

**Limit:** both agents reached their models through the user's own gateways. Claude used `ANTHROPIC_BASE_URL` from `~/.claude/settings.json`. Codex used a custom `model_provider` with ChatGPT auth. A plain subscription login going straight to Anthropic or OpenAI was not exercised.

`settings.json`, `settings.local.json` and `~/.codex/config.toml` have identical checksums before and after. `~/.claude.json` changed, but other sessions write to it too, and it has no entry for the spike cwd. Codex wrote its normal rollout into `~/.codex/sessions`. Claude wrote no transcript because of `persistSession: false`.

## 2a. MCP server per session

**Run, both.** A stdio entry `{name, command, args, env: []}` in `session/new` `mcpServers` was connected and called.
- Claude exposes the tool as `mcp__spike__echo`. Claude Code first sent MCP `server/discover` (protocol 2026-07-28). After a method-not-found reply it fell back to `initialize` with protocol 2025-11-25.
- Codex sent `initialize` with protocol 2025-06-18 and reported the call as `tool_call` with title `mcp.spike.echo` and kind `execute`. Neither agent asked for permission. Claude did not ask because of `allowedTools`. Codex did not ask either; the tool had `readOnlyHint: true`.
- **Read:** codex-acp rejects the `sse` and `acp` transports and accepts stdio and http.

## 2b. Turning off shell, file writes and web

**Claude, run.** Mechanism: `session/new` `_meta.claudeCode.options = {tools: [], strictMcpConfig: true, allowedTools: ["mcp__spike__echo"], allowDangerouslySkipPermissions: false, persistSession: false}`, plus `_meta.claudeCode.emitRawSDKMessages: [{type:"system",subtype:"init"}]` to see the tool list. The init message listed `tools: ["mcp__spike__echo"]` and only the `spike` MCP server. The user's 7 plugins, 74 skills and 10 agent definitions still loaded, but no tool can reach them. Asked to run `ls` and create `probe.txt`, the model answered that it had no shell or file tool; the answer came in Czech, which shows the user settings applied. Nothing was written.
**Read:** any tool missing from `allowedTools` goes through `canUseTool`, which sends `session/request_permission`. The adapter warns that bare `allowedTools` entries skip that callback. The adapter's default `settingSources` is `["user","project","local"]`, so user and project hooks, plugins, CLAUDE.md and model settings apply. `settingSources: []` would also drop settings-based env such as this user's gateway auth, so it is not a blanket fix.

**Codex, run.** Mechanism:
- `INITIAL_AGENT_MODE=read-only`. Every turn went out with `approvalPolicy: on-request`, `approvalsReviewer: user`, sandbox `readOnly` and `networkAccess: false`. The default mode `agent` uses an `auto_review` reviewer instead of the user.
- `CODEX_CONFIG` with `features` `shell_tool`, `unified_exec`, `apps`, `plugins`, `hooks`, `multi_agent`, `image_generation`, `browser_use` and `computer_use` set to `false`, and `web_search: "disabled"`.

The model's own tool list, read from the rollout, had no shell. It had `apply_patch`, `view_image`, goal, clock and MCP-resource tools, plus MCP tools. Its `apply_patch` for `probe.txt` produced `session/request_permission` (kind `edit`). The client picked the only reject option, `cancel`, and the turn ended. The file was not created.
Caveats (run):
- The user's MCP servers can't be reliably excluded. The adapter overwrites a nested `mcp_servers` key in `CODEX_CONFIG` with the session's servers. Dotted keys `mcp_servers.<name>.enabled=false` reached Codex, yet three of the user's own servers (a deploy tool among them) still connected, and their tools were in the model's list.
- Codex ran in code mode: it calls tools from JavaScript inside a built-in `exec` tool. Three scripts that only listed tools never appeared as ACP tool calls. Only the inner MCP call and `apply_patch` did.
- After the first turn the adapter starts an ephemeral title thread (model `gpt-5.6-luna`) and passes it the user's prompt. That thread ran with the user's own config: `approvalPolicy: never`, `dangerFullAccess`, and the user's plugin hooks ran. None of the overrides above reach it. **Read:** it is skipped only when the session already has an explicit title (`/rename`).
- The adapter marks cwd trusted (`projects.<cwd>.trust_level = "trusted"`, seen in `thread/start`). Codex also loaded `AGENTS.md` from the git root above the cwd.

## 2c. Cancel

**Claude, run:** `session/cancel` sent mid-stream got a prompt response with `stopReason: "cancelled"` 8 ms later. One update was already in flight. None arrived in the next 4 s.
**Codex:** `session/cancel` latency was **not measured**, because the prompt budget ran out. Denying the edit ended the turn 6 ms after the client's answer. **Read:** `session/cancel` maps to app-server `turn/interrupt`.

## 2e. Streaming

**Run.**
- Claude sent `agent_message_chunk` (20 chunks for the second answer), `tool_call` (`pending`), then `tool_call_update` with `rawInput` and finally `completed` with content. It also sent `usage_update`, `available_commands_update` and `session_info_update`.
- Codex sent token-sized `agent_message_chunk`, `tool_call` (`in_progress`) and `tool_call_update` (`completed`/`failed`). It also sent `usage_update`, `session_info_update` (thread status, title) and `available_commands_update`.

**Read:** both adapters can also emit `agent_thought_chunk`, `plan`, `current_mode_update` and `config_option_update`, and extension kinds after negotiation (`subagent_*`, `async_task_*`, `notice`). The Rust client must ignore unknown kinds.

## Terms (read, fetched 8 Oct 2026)

**Anthropic.** Claude Code "Legal and compliance" (code.claude.com/docs/en/legal-and-compliance, undated): "Anthropic does not permit third-party developers to offer Claude.ai login into their own applications, or to route requests through Free, Pro, or Max plan credentials on behalf of their users. Moreover, developers may not collect, store, or intermediate Claude.ai credentials or session tokens". The same section continues: "Nor does it prevent an end user from signing in to the unmodified Claude Code binary with their own Claude subscription". The Agent SDK overview says: "Unless previously approved, Anthropic does not allow third party developers to offer claude.ai login or rate limits for their products, including agents built on the Claude Agent SDK." Help Center article 15036540, updated 7 Oct 2026: "You can still use the Claude Agent SDK, `claude -p`, and third-party apps with your subscription limits."
**Assessment: unclear.** Nuzky running the user's unmodified installed `claude`, never touching credentials, fits the second sentence and the Help Center. The adapter, though, is a product built on the Agent SDK. The adapter itself ships `--hide-claude-auth` ("this integration must never bill a claude.ai subscription"), so at least one integrator had to block subscription billing. Ask Anthropic before shipping and keep an API-key path. The SDK and its binary can't ship inside the GPL release; install them on the user's machine.

**OpenAI.** The Sign in with ChatGPT docs (developers.openai.com/siwc/token-sharing-open-source, undated) offer plan usage "for open-source and locally hosted apps" without applying. For app-server the app runs its own OAuth and passes `ACCESS_TOKEN`: "No separate Codex sign-in is required." The Codex auth docs (learn.chatgpt.com/docs/auth) say "The CLI and extension share the same cached login details" and "Treat `~/.codex/auth.json` like a password".
**Assessment: unclear but lower risk.** I found no text on a third-party app running the user's own installed Codex under its existing login, which Zed and JetBrains do. The documented route for an open-source app is Sign in with ChatGPT with its own token. **Run:** Codex records `clientInfo.name` as the originator (`capopen-spike` in the rollout; the app was still called CapOpen then), so OpenAI sees which app drives it.

## Open risks

1. Churn. claude-agent-acp shipped 0.86.0 (5 Oct) to 0.88.0 (8 Oct). codex-acp went from 2.0.1 (29 Sep) to 2.1.1 (1 Oct). The Rust crate had two major bumps since July. Pin exact versions and rerun this spike on every bump.
2. Codex has to use its bundled binary, so expect version skew with the user's install. That is about 290 MB per platform and a second Codex next to the user's.
3. Node >=22 is required at runtime; neither adapter publishes standalone binaries.
4. Isolation from the user's own setup. Codex lets in user MCP servers and the full-access title thread. Claude still runs user and project hooks and plugins. Both trust the cwd and load AGENTS.md or CLAUDE.md from parent folders. Untested mitigation: an empty cwd owned by Nuzky and, for Claude, `settingSources: ["user"]`.
5. Codex code-mode `exec` hides intermediate calls, so the "agent run is visible live" rule holds only partly. Denying an edit ends the whole Codex turn.
6. When `APP_SERVER_LOGS` is set, codex-acp writes the whole Codex config to disk, secrets included (seen: a provider bearer token and MCP env tokens). Never set it in Nuzky.
7. A fresh `CODEX_HOME` downloaded about 93 MB of plugins on first start, which matters if Nuzky gives Codex its own home.
8. Not verified: the direct subscription path, Codex `session/cancel` timing, real usage-limit responses, the Claude adapter installed with `--omit=optional`, Claude permission prompts for built-in tools, macOS and Windows.

**Outcome (8 Oct 2026):** the panel does not use ACP; see docs/AI-ARCHITECTURE.md, "AI panel".
