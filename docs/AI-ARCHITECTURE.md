# AI architecture

Nuzky is built around AI the user brings: any MCP-capable agent can edit a project, live in the open app, and the in-app AI panel runs the user's installed Claude Code under their own login (Codex comes next). Connect agent covers Claude Code and Codex in a terminal. Research behind these decisions: [docs/research](research).

Decided on 6 Oct 2026 after two independent proposals and a cross-critique, and refined the same day after the headless MCP landed (two more proposals and a cross-critique).

## Principles

- **One editing authority.** Every change, from the UI, an agent or the CLI, goes through `ProjectSession` and the existing `EditCmd` validation. Agents never write the project JSON directly.
- **Live, reversible runs.** An agent's changes appear in the app as they happen. A whole run is one undo step. Review is available but never required to finish a run.
- **Deterministic primitives, creative agents.** Timing-critical work (ripple cuts, caption timing, transcripts) is done by engine tools; the agent decides what to do and checks rendered frames.
- **Local first.** Editing, analysis, transcription and export run on the machine. A cloud model only sees what Nuzky sends it: prompts, tool results, transcripts and frames.

## Processes

```
Claude Code / Codex / Gemini / Cursor ──stdio──▶ nuzky-app mcp --project P ──IPC──▶ Nuzky app (Host for P)
                                                         │
                                                         └─ no app running: its own Host for P
```

- `crates/session` holds `Host`: the `ProjectSession`, the one job system and the transcript store. The app owns one shared Host; each connected MCP client has a separate access level and run ownership. A headless bridge creates its own Host. The desktop export/captions/transcript jobs still use `src-tauri/src/jobs.rs`; migrating those jobs is separate work. `ProjectSession` owns the live `Editor` and its history, revision, session epoch, the open run, the writer thread and crash recovery. It has no Tauri dependency.
- The bridge is `nuzky-app mcp --project <path> [--allow-write]`, handled before Tauri starts, so agents run the installed app's own version; `nuzky mcp` is the same code for development. The bridge serves the MCP catalog, guide and schema itself and sends each tool call to the app, or to its own Host when no app owns the project.
- IPC: a Unix domain socket (`$XDG_RUNTIME_DIR/nuzky/<project-hash>.sock`, directory 0700, files 0600) on Unix. Windows currently always uses a headless Host; a user-restricted named pipe is planned. Newline-delimited JSON: a hello `{nuzky: 1, token, client, access}` answered with the session epoch, then `{id, tool, args}` → `{id, result}`. The 32-byte random token is hex-encoded in `<project-hash>.token` next to the socket and rewritten on every open. The directory is 0700 and both files are 0600. Without XDG_RUNTIME_DIR, the directory is `<temp>/nuzky-<uid>`. Nothing listens on the network.
- Access is per client: a read-only client never takes the lock and mutating tools return `READ_ONLY`. It may cancel a job it started itself, such as a long `activity`.
- Ownership is an OS lock on `<project>.lock`. A writable headless bridge currently holds it for its lifetime. The bridge chooses app IPC or headless once at startup. If an attached app closes or switches project, later tool calls return `APP_CLOSED` and require restarting the agent's MCP server. Releasing an idle headless lock and retrying read-only app opens are planned.
- The session reports changes as events on a channel, never calling out while holding its lock. The app forwards them to the preview and the frontend, which ignores snapshots older than the one it has within the same session epoch. The revision changes only when the project does.

## Runs and undo

A run groups one agent turn. There is one linear history: a run is one entry in it, between the user's own edits.

- `begin_run(label)` seals the history, writes `<project>.checkpoint.json` and returns `run_id`. Mutations are only accepted from the run that owns the session. Manual edits, Undo and Redo in the UI are blocked with "AI is editing · Stop"; the toast offers "Stop and edit", so stopping the AI is always deliberate.
- `apply_edits(run_id, request_id, edits[])` applies a batch atomically to the live project under the run's coalesce key `run:<id>`, so the whole run merges into one undo entry. A repeated `request_id` with the same content returns the stored result; with different content it is an error. The result lists created, changed and removed clip ids and the real times after magnetic repacking, and is returned only once the project is on disk.
- `end_run(run_id, keep | discard)`: keep seals the entry; discard drops it without a redo entry. A run also ends with keep when its client disconnects or after 2 minutes without calls from that client; reads by the UI or other clients do not keep it open.
- Stop in the UI revokes the run first (late calls get `RUN_STOPPED`), cancels its jobs, then ends it with keep. Ctrl+Z then undoes the whole run and Ctrl+Shift+Z brings it back.
- `undo_run(run_id)` works only while that run is the last history entry.
- Versions outlive the session. Each kept run, each user step (one undo entry), undo, redo, restore and the project as it opened becomes a version: the project's compact JSON, its SHA-256, a label, the time and the run id. A step with a coalesce key (a drag, a typing burst) becomes one when the next step starts, and until then `list_history` shows it first under the index it will get; an open run becomes one when it ends; a discarded run never. The writer thread appends them to `<project>.history.jsonl`, one JSON line each, after the saves before them; a line whose project an earlier line holds leaves it out. The newest 200 versions and 32 MiB of distinct project JSON are kept, and once the file holds twice that it is written again atomically with only those. Reading skips a torn or unreadable line and a line whose project no longer matches its hash, and the next write replaces the file; a versions file that is a link is never read or written through, only replaced. A failed write shows as "Not saved" until a later one succeeds. A project that opens different from its newest version (an older project, or a save that never reached the file) becomes the version "Opened".
- `list_history(limit)` lists the versions newest first with the current hash. `undo_to(index | hash prefix)` validates the stored project and replaces the current one as one undo step; it needs no open run (`RUN_ACTIVE`), like Undo in the app.
- Every result carries `revision` and `session_epoch`; mutations may pass `expected_revision` to fail fast on stale state.
- User edits are saved shortly after they stop; run batches are saved before they are acknowledged.
- On open, a leftover checkpoint means a run did not finish: the app asks to keep the AI changes or restore the version before, as an undoable edit. Headless mode refuses writes until that is resolved.
- Agents never set the user's selection.

## Transcripts

- A transcript belongs to a media file, not to a timeline: words with times in the file's own (source) time, stored once in `<data dir>/nuzky/transcripts/<fingerprint>.json`. The fingerprint hashes the file size, its first and last MiB, and 32 evenly spaced 64 KiB chunks. The same file in several projects is recognised once and a moved file keeps its transcript. Version 2 records also store duration_us; version 3 records also store `alignment`, the word timing model that measured the words (null when they are Whisper's estimates). Version 2 records still read, as estimates, so an existing transcript and the word corrections keyed by its words stay; version 1 records and duration differences over 1 ms are treated as missing.
- Whisper's word times are estimates, 100–300 ms off in connected Czech speech. Right after recognition, `transcript::recognise` measures them in the sound with the word timing model of the recognised language (`nuzky_analysis::Aligner`, a wav2vec2 CTC model with Viterbi alignment of Whisper's text; Czech and English), downloaded on first use with a pinned SHA-256 like the Whisper models, and the record stores those times. The job shows the download ("Downloading word timing model" in the app, `downloading_word_timing_model` for agents) and the measuring ("Measuring word times", `measuring_word_times`); a stop ends either within a second. Without a model for the language, offline, or when the model fails to load, the words keep Whisper's estimates moved into the nearest pause by `nuzky_analysis::align_words` (a pause wins over a consonant's closure; without one, the quietest moment within 60 ms), as before; `transcribe` reports `word_times: "estimated"` instead of `"measured"`. Words the model cannot spell (numbers, acronyms) share the gap between their measured neighbours. Existing transcripts are not measured again, since word corrections are keyed by a word's start; recognising a file again measures it. Cut margins, pauses and captions all count from the stored times.
- What the timeline says is always derived: `engine::speech::map_words` maps the words of every heard clip (unmuted track, volume above 0, a video asset with sound, detached sound included) through its source range and speed. Cuts, slivers, speed, undo and redo are therefore always right, and a transcript never goes out of date; the only note left is "N clips not transcribed".
- `get_transcript` and `edit_transcript` use `transcript_key`, which includes recognised words as well as their timeline layout. `get_state` exposes `speech_layout_key`; `apply_edits` accepts it as `expected_speech_layout_key`, a hash of exactly what `map_words` reads. The session rejects it with `SPEECH_CHANGED` when the speech moved in the meantime, and accepts it after unrelated edits such as a caption restyle.
- Misrecognised words are corrected in the project, not in the shared store: `word_corrections` lists the media file, the word's start in it, the recognised text and the correction. Deriving applies them to the source words before `map_words`, so `get_transcript`, `analyze retakes`, captions built again and the app's transcript all read the corrected text. A correction applies only to the word with that start and recognised text: after the file is recognised again differently it does nothing and never lands on another word. `CorrectWords` sets them; the app and `correct_words` plan it once (`plan_correction` in `crates/mcp/src/transcript.rs`) together with the caption clips that show the word, as one undo step.
- Tracks have `keep_in_place`; `RippleDeleteRanges` without `keep_track_ids` uses it, so agents cut the way the UI does and leave music alone.

## Tools

All times are integer microseconds on the timeline unless a field says `source`. Ranges are `[start, end)`.

| Tool | Purpose |
|---|---|
| `get_state(range?, clip_ids?)` | Project, tracks, clips with ids and times, the user's selection and playhead, revision, open run |
| `begin_run(label)` / `end_run(run_id, action)` / `undo_run(run_id)` | Run lifecycle |
| `list_history(limit?)` / `undo_to(index \| hash)` | Kept versions of the project, and restoring one as a new undo step |
| `get_style()` / `change_style(action)` | The creator's style as Your style shows it, and changing it once the creator agreed: their own rule in their words, accepting or rejecting a suggestion, removing or reverting a rule, the whole text, or a version. No run, no project change; every change is a version labelled AI: |
| `apply_edits(run_id, request_id, edits[], expected_revision?)` | Atomic batch of `EditCmd` |
| `import_media(run_id, paths[], request_id?)` | Probe local files and add them as assets; a repeated `request_id` never adds them twice |
| `inspect_frames(times_us[] or sample: "changes", width?, safe_area?)` | Rendered frames as one image (contact sheet with timestamps); fails if media is missing. `sample: "changes"` picks the frames itself: it looks at up to 120 candidates of a range, compares their difference hashes and keeps only frames unlike the last four kept, at most 16 per page, with the number skipped and a `next` cursor that carries those hashes, so the next page repeats nothing |
| `activity(range_us?, points?)` | Text only: per step of the range the biggest picture change and the motion (the picture difference `scenes` uses, from tiny renders of the timeline as exported), the loudness of the mix and the peaks of each. A job that answers in the same call when it finishes within 10 s; a longer range hands over the job to poll or cancel |
| `analyze(kind, asset_id?, params)` | `silences`, `loudness`, `scenes`, `fillers` of one asset as a job, from `crates/analysis`. `retakes` reads the stored words of the whole timeline and answers at once, also to read-only clients: groups of attempts at one restarted sentence with the last complete one to keep, also restarts inside one sentence, fillers that start a sentence, attempts that trail off before a new sentence, near-repeats that differ in a negation, a number or a content word for review, and `suggested_delete` word ranges for `edit_transcript`. It fails with `TRANSCRIPT_MISSING` while a heard clip lacks words. `emphasis` answers at once the same way: sentences for a punch-in, scored by how much louder they are than the median sentence (measured in each word's own file), an exclamation and the opening hook, 1.2–8 s long, at least 5 s apart and about one per 12 s, with a scale of 1.15–1.3. When a file's sound is not prepared yet, it starts a job that prepares it and answers `AUDIO_NOT_READY` with the job, since decoding inside the call could not be stopped |
| `analyze(kind: "thumbnail_frames", params.format?)` | Job picking frames for a cover from the timeline as exported without text tracks (`crates/vision`). A look every 0.25 s at 384 px (sharpness, exposure, YuNet faces) away from cuts, transitions and clip animations shortlists 40 moments; a closer look at 1280 px scores them with MediaPipe Face Mesh and blendshapes (eyes open, lips apart, gaze and head turn, smile against this face's usual look, face sharpness) and framing for a 9:16 cover (safe area, 3:4 profile grid) and a 16:9 thumbnail. Returns 6–8 candidates at least 2 s apart with every part of the score, faces, the person's box (Selfie Segmenter) and both crops. Open to read-only clients |
| `segment_subject(time_us)` | Job masking the subject of one frame with BiRefNet_lite as an 8-bit grayscale PNG at canvas resolution in the cache, keyed by the rendered frame and the model, so the same frame and edit reuse it; returns the box, the share of the canvas and whether a face is there. Stopping it ends the inference within tens of milliseconds. Both tools need their models installed (`nuzky vision-models`, or the app's `start_vision_models` job); `MODEL_MISSING` names what is missing and neither downloads |
| `inspect_thumbnail(format, width?, safe_zones?)` | The project's cover (`cover_9x16`) or YouTube thumbnail (`youtube_16x9`) as one PNG, drawn by the same function as `export_thumbnail` and the CLI (`Renderer::render_thumbnail` in `crates/engine/src/thumbnail.rs`), with the share of each text behind the person that they hide. `safe_zones` tints what the Reels interface, the 3:4 profile grid and YouTube's duration badge cover. Only reads: a mask that is not cached yet is started as a `segment_subject` job and the call answers `MASK_NOT_READY` |
| `export_thumbnail(format, path)` | Job writing the thumbnail at full size to a new `.png` or `.jpg` through a `.nuzky-part-*` file, making the mask first when needed; JPEG takes the best quality under YouTube's 2 MB |
| `transcribe(asset_ids?)` | Job recognising the heard media that has no transcript yet |
| `get_transcript(range?)` | Numbered timeline words and sentences, `transcript_key`, untranscribed clips |
| `edit_transcript(run_id?, transcript_key, keep or delete word ranges, dry_run?)` | Cuts by word numbers with tight padding and shortened pauses; returns the new duration and text. A dry run needs no open run |
| `correct_words(run_id, transcript_key, corrections[{i, text}], request_id?)` | Corrects misrecognised words by number; captions showing them change in the same step and captions built later keep it |
| `apply_zooms(run_id, transcript_key, zooms, request_id?)` | Punch-ins on word ranges as one `ZoomRanges` edit: each range runs from midway into the silence before its first word to midway into the silence after its last (at most 150 ms out), or on to the cut when only silence lies between, so no piece of a take is left without words; `SPEECH_CHANGED` on a stale key, retry-safe by `request_id` |
| `apply_motion(run_id, kind, strength, clip_id? or range_us?, request_id?)` | A slow camera move as one `ApplyMotion` edit: Push in, Pull out or Ken Burns, written as two keyframes on a smooth curve from each clip's transform, zoomed about the middle of the safe area on vertical canvases; over a range the main-track clips under it move as one continuous motion. Clips with keyframes are left alone and listed in `skipped` |
| `propose_reels(run_id, transcript_key, candidates[{from, to, title, why, score}], max_duration_us?, request_id?)` | Reels from a long video (`crates/mcp/src/reels.rs`): moments that work on their own, as one `SetReelCandidates` edit that replaces the candidates not made yet. Each is checked against the transcript: inside it, from a sentence's first word to a sentence's last (a comma ends none), sharing no words, and at most 60 s by default once cut. The tool fills in the times, the hook (the opening sentence) and the length of the reel the cut gives |
| `make_reels(run_id, ids, canvas?, request_id?)` | Writes a new project beside the source for each candidate, never replacing a file or reusing a leftover history: the same media, only the candidate's words cut as `edit_transcript` keep cuts them, on a 1080x1920 canvas, `crop` (the middle fills it) or `blur` (all of it over a blurred copy). Then one `UpdateReelCandidate` per reel marks it made with its path; when that edit is refused, the new projects go again. The app's `make_reels` command runs the same function as a user edit. A framing that follows the face would be another `canvas` value |
| `build_captions(run_id, style?, max_words?, max_chars?)` | Deterministic caption clips on one captions track, never across a cut; the Reel style by default |
| `export_video(path, preset? or resolution + fps, quality?)` | Job exporting a snapshot; a preset (`reels`, `shorts`, `youtube_1080p`, `youtube_4k`, `instagram_feed`, `square`) writes the platform's size and frame rate with the sound levelled to -14 LUFS, true peak at most -1 dBTP, and needs its canvas ratio |
| `job(job_id, get | cancel)` | Progress, result, cancel |

`RippleDeleteRanges { ranges, keep_track_ids? }` cuts the ranges out of every track except the kept ones and closes the gaps, so video, overlays, audio and captions stay in sync. `AddCaptions` never deletes other tracks. `ZoomRanges { ranges: [{startUs, endUs, scale}] }` splits main-track clips at the range edges and multiplies the scale of the pieces inside, keeping position and rotation; an edge that would leave a piece under 0.3 s, or cut a transition, animation or fade short, moves to the clip's edge, split halves play their sound on unchanged, and clips with keyframes are left alone and listed in the outcome's `skipped`. `SetThumbnail { thumbnail }` replaces the project's thumbnail of its format and `RemoveThumbnail { format }` removes it; `RippleDeleteRanges` moves a thumbnail's frame time with the picture, so it keeps showing the same moment. `SetReelCandidates { candidates }` replaces the reel candidates and `UpdateReelCandidate { candidate }` replaces the one with its id; validation keeps them apart, with single-line texts, and a made one with an absolute project path. Their words and times stay as proposed, so a candidate whose speech moved since is refused by `make_reels` with `SPEECH_CHANGED` instead of cutting the wrong words.

Resources: `nuzky://guide` (the editing skill), `nuzky://schema` (project JSON schema) and, when the creator has one, `nuzky://style` (their `EDIT.md`). Prompts: `edit_selected(goal)`, `thumbnail(wishes?)`, which picks the frames, writes a hook from the transcript and makes, checks and exports both covers in one run, and `rough_cut(wishes?)`, which runs the whole way from raw takes to an exported reel (in Claude Code: `/mcp__nuzky__rough_cut`).

## Creator style

- `nuzky style learn <recording> <cut>...` turns pairs of a raw recording and the creator's finished cut into `<data dir>/nuzky/EDIT.md`: what gets cut (restarted sentences, repeats, slips, fillers, dropped passages, calls to action), pauses, pace, cuts, captions and zoom, each rule in numbers and shown on at least three moments of the recordings. Rarer things are listed as seen, not as rules. The same input always gives the same file, and an existing file is only replaced with `--replace`, since the creator may have edited it. Written to the default place, it becomes a version of the style (below) and keeps the creator's own rules; `--out` elsewhere writes the plain file.
- `nuzky style learn --from <timeline.otio>` learns from timelines the creator cut in another editor instead. `crates/interchange` reads a timeline file into a neutral `ImportedTimeline` (tracks, media clips with their source in and out, place on the timeline, speed, volume, framing and keyframes, transitions, text clips and markers) and lists in plain words what it did not read; each format has its own module. OpenTimelineIO's JSON is read with serde alone (`otio.rs`): every `RationalTime` is turned into microseconds at its own rate, media with a timecode counts from its available range, a time warp changes how much media a clip plays but not its length, gaps and nested sequences keep their time, and only local files are media, so a web address or a share on another computer in a shared file is never touched. OTIO has no standard for framing, volume or titles, so those are not read from it. `style/from_timeline.rs` turns the timeline into what learning reads: each recording whose sound the timeline plays (on its audio tracks, or else its lowest video track; video above that is B-roll) is a source of its own, its clips on the tracks that play its sound (a clip that only repeats another, such as a second channel, left out) are the pieces with a full match, the recognised words are moved through them as `map_words` does, and pauses are gaps of 80 ms or more between words, a gap where another recording speaks being no pause. The finished video is the whole timeline, its gaps and B-roll shared among the recordings by how much each plays. A piece maps cut time to the recording one to one, so for a sped up clip only its start is exact, while its words are placed at their speed. A recording played whole teaches no cutting. In the app, Learn my style does the same with Projects (.otio) and shows `EDIT.md` as learned; nothing is kept until the creator uses it, which writes the style through `Store::replace` only over the version the preview was made over (over an existing style only after they agree) and keeps the evidence.
- The style lives beside `EDIT.md` in `<data dir>/nuzky/style/` (`crates/mcp/src/style.rs`). `evidence/` holds what was learned from each video, enough to learn everything again: the recording's and the cut's words, where the cut's pieces came from, its pauses, captions and framing. Learning the same video again replaces its evidence, and the newest 12 videos are kept. `versions.jsonl` holds every version of the style, newest last: the text, what each accepted rule decided and which rules learning leaves alone. Learning only adds evidence and never writes `EDIT.md`; the rules learned from all evidence that are new, or whose decisions (a pause length, the filler words to cut, caption limits, zoom; numbers within 15 % or a small floor count as the same) differ from what was accepted, are suggestions. Accepting one writes its section and its Settings rows into `EDIT.md` where `learn` would put them, so accepting everything learned from some pairs gives the same bytes as `nuzky style learn` on them. Rejecting, removing or reverting a rule, or changing it by hand, makes learning leave it alone until the creator asks to learn it again. Under `## Your rules` the creator writes their own instructions; learning never touches them. A change made to `EDIT.md` outside Nuzky is recorded as a version too. Every writer holds `style/lock`; the version is written before the file, and a file not written yet is finished by the next change.
- Nuzky learns by itself, on this computer only, after every export (in the app and through `export_video`) and 10 s after the user's last edit of a project an AI run cut and the run was kept (or when the project is switched or closed before then). It reads the project, not the exported file (`project_evidence`): the recording is every transcribed video the project hears, one after another; the words its heard clips play and where are exact, from `map_words`; each heard clip is a piece; pauses are gaps of 80 ms or more between words; captions come from the Captions track, framing and zoom from the main track's transforms and keyframes, and the words the user corrected become the Spelling rule, which `nuzky style learn` never writes. Nothing is learned while an AI run is open, from a project that plays everything it recorded, or from one that teaches exactly what the AI's last kept run left: the AI would only learn its own cut. Edits that undo the run teach nothing either, while an export of the user's own cut from before the run does.
- `EDIT.md` is parsed into blocks at the headings `learn` writes (`crates/analysis/src/style/doc.rs`). Anything else, such as the creator's own sections or a rule's subsections, belongs to the block above it.
- Where the cut came from is found by sound (`crates/analysis/src/style/align.rs`): the spectral shape of 20 ms windows, which a clip's own volume does not change, matched by a Viterbi path over candidate places in the recording. Retakes repeat the same words, so text alone cannot place a cut. A recording word counts as kept when its middle lies in a kept piece, or when the cut's own recognition heard the same word within a second of it: recognition times can be that far off next to pauses, where cuts are.
- Captions are found in the cut's picture as white pixels next to black ones, in the band where they are most common, and their words are counted from the gaps between them. Zoom and framing compare each moment of the cut with the same moment of the recording; scale, x and y are in Nuzky transform terms.
- The MCP server reads `EDIT.md` on each request, so an agent gets exactly the accepted style with the creator's own rules and never a suggestion. With it, the instructions start with a pointer to the style, and the instructions, `nuzky://guide` and `edit_selected` end with it; `nuzky://style` serves it alone. Its rules override the guide's defaults, and the creator's own rules win over everything. Without it, everything is exactly as before.
- `nuzky style compare <recording> <cut> <project>` scores a project by the recording's words: recall is the share of the creator's kept words the project plays, precision the share of the project's words the creator kept. It also lists the passages that differ.
- Recordings, transcripts and `EDIT.md` stay on the computer. An agent connected through MCP reads `EDIT.md`, which quotes the recordings, the same way it reads transcripts.

## Agent setup

- The app ships `skills/nuzky-edit/SKILL.md` and an `AGENTS.md` template: units, magnetic main track, ripple behaviour, analyse → edit → inspect frames → export, and never editing the JSON directly.
- Connect agent ("Connect an agent in a terminal…" in the AI panel's agent menu) writes one `nuzky` MCP server into Claude Code's user settings (`~/.claude.json`, or `$CLAUDE_CONFIG_DIR/.claude.json`, under `mcpServers`) and Codex's (`~/.codex/config.toml` or `$CODEX_HOME/config.toml`, as `[mcp_servers.nuzky]`): this app's executable (the AppImage itself when it runs from one) with `mcp --current --allow-write`. The file is copied to `<file>.nuzky-backup-<unix time>` first and replaced in one step; a symlinked config is written where the link points, every other key keeps its exact text (Codex comments included), an entry that already runs this app is left alone, and a file that does not parse is not touched. Code: `src-tauri/src/connect.rs`.
- `--current` attaches to the project open in the app: each app listener writes the open project's path to `current` next to its socket (0600 in the 0700 endpoint directory) and removes it when the project closes. With no project open the bridge refuses to start (`APP_NOT_RUNNING`) instead of editing headless, so one configuration serves every project; the agent's MCP server is restarted after switching projects.
- Planned: the same for Gemini CLI, Cursor and Claude Desktop.
- Planned diagnostics will check, in order: executable found, config parsed, MCP handshake, project attached, `get_state` and one `inspect_frames` call.

## AI panel

Decided on 8 Oct 2026, replacing the ACP plan of 6 Oct, after an ACP spike ([research](research/2026-10-08-acp-spike.md)), two independent proposals and a cross-critique. ACP adapters are npm-only and need Node 22 at runtime, the Claude adapter is a product built on the Agent SDK, whose subscription terms are unclear, and codex-acp needed its own bundled Codex and let the user's MCP servers and a full-access title thread into the session. Driving the installed CLIs directly needs none of that.

- **One process per message.** `crates/agent` finds the agent (`NUZKY_AGENT_CLAUDE`/`NUZKY_AGENT_CODEX` override, `PATH`, then the usual install folders), starts it for one message and parses its output into `text`, `tool` (running, done, failed, with its arguments), `done {stopped}` and `error {code}` events; `src-tauri/src/agent_panel.rs` forwards them to React as `agent` events with the chat id. The next message continues the conversation with the agent's own resume (Claude `--session-id`, then `--resume`; Codex `exec resume <thread id>`, with the id it reports once it has kept the conversation, which a turn that failed before anything happened has not). A turn that never got going starts a fresh session next time.
- **Claude Code** runs as `claude -p --output-format stream-json --include-partial-messages` with `--setting-sources user` (the user's login, model and gateway stay; the folder's settings, hooks and MCP servers do not), `--settings {"disableAllHooks":true,"outputStyle":"default","autoMemoryEnabled":false}`, `--strict-mcp-config` with only `nuzky` (this app's executable with `mcp --project <the window's project> --allow-write` and an explicit `XDG_RUNTIME_DIR`; `--current` would name the project another Nuzky window made current last), `--tools ""`, `--allowedTools mcp__nuzky --permission-mode dontAsk`, `--disable-slash-commands` and a short appended system prompt. Its folder is an empty 0700 `nuzky-agent` under `XDG_RUNTIME_DIR` (else the temp folder), outside the home folder, so no CLAUDE.md or AGENTS.md above it loads. Variables of a parent Claude Code session are removed from its environment.
- **Codex** runs as `codex exec --json` (`codex exec resume --json … <thread id>` later) with the message on stdin, `--ignore-user-config` (the login in `CODEX_HOME` stays; `config.toml` with the user's MCP servers, plugins, hooks, provider and model does not), `--ignore-rules`, `--skip-git-repo-check`, and `-c` settings: a read-only sandbox with `approval_policy="never"`, web search, the shell, apps, plugins, hooks, other agents, image generation, image viewing and the remaining tools off, `nuzky` as its only MCP server (the same bridge as Claude's, `required`, with `default_tools_approval_mode="approve"`, without which Codex holds back every Nuzky call for an approval it cannot ask for), Nuzky's tools offered directly (`features.code_mode.direct_only_tool_namespaces=["mcp__nuzky"]`: current models otherwise call tools from JavaScript in `exec`, and `--json` reports none of those calls) and the same short prompt as `developer_instructions`. Settings go through `-c` rather than `--disable`, because Codex refuses to start on a feature name it no longer knows but only warns about a setting. Checked on codex-cli 0.162.1 by capturing what it sends the model and asking it to list its tools: only Nuzky's, plus `exec` holding `apply_patch` (refused by the read-only sandbox), the clock and reading Nuzky's own MCP resources. Kept, the user's `config.toml` would have left every MCP server in it callable from `exec`, even with the table replaced by `-c`. Codex sends an answer only whole, message by message, not word by word. Planned before as `codex app-server`, which keeps the user's provider and streams words; `exec` is Codex's documented non-interactive mode, and leaving the user's configuration out entirely is a stronger guarantee than turning their servers off by name.
- **Fail closed.** The turn stops as an error when Claude's `init` lists a tool that is not `mcp__nuzky__*`, when `nuzky` is not connected, or when `output_style` is not `default` (Claude silently ignores settings it does not accept, which would also drop `disableAllHooks`), and when Codex reports anything but its answer, its reasoning or a call to `nuzky`: a command, a file change, a web search, another agent or another server's tool.
- **Stop** (the panel's Stop, Stop and edit in the top bar, opening another project, quitting) ends Nuzky's run first, so the editor unlocks at once and late calls get `RUN_STOPPED`, then sends SIGINT to the agent's process group, its MCP bridge included, and SIGKILL after 2 s. Both agents record an interrupted turn on SIGINT, so the conversation can go on (Codex 0.162.1 stopped within 0.2 s in the middle of a tool call and remembered the turn when resumed).
- **Problems:** a missing executable is `NOT_INSTALLED`; Claude's `authentication_failed` is `NOT_SIGNED_IN` and `rate_limit`/`billing_error` is `USAGE_LIMIT`, with the agent's own text (it names the reset time). Codex with no login at all retries for half a minute, so its first `Missing bearer` error ends the turn as `NOT_SIGNED_IN` at once, and the panel says to run `codex login` and choose Sign in with ChatGPT; a failed turn with `401 Unauthorized` or "sign in again" is `NOT_SIGNED_IN` too, one with "usage limit" or "spend cap" is `USAGE_LIMIT`. Anything else is `AGENT_FAILED` with the agent's message or its last error lines. The panel puts a message that failed before an answer back into the field.
- **What changed:** the session keeps the project as the run began and, when the run ends, sends `RunSummary` before `Run(None)`: lines from `nuzky_session::summary` comparing before and after (length, passages cut, takes removed, media added, captions, texts, zooms, splits, volume, speed, colour, fades, Clean voice, Lower under speech, motion, animations, transitions, tracks, canvas, word corrections, imports), each with the clips it is about and where. The panel shows them under the run with Undo instead of the "AI edit done" toast.
- **Your style:** from the Your style page the panel sends the message with `style: true`, so the agent is told it is about the creator's style for all their videos, not the open project; it reads the style with `get_style` and changes it with `change_style`. The app watches the style's files (EDIT.md, `style/versions.jsonl`, `style/evidence/`) twice a second and shows any change at once, whoever made it.
- **Choices:** `suggest_options` (MCP, reads only) lets the panel's agent offer 2–6 choices (an agent in a terminal asks in text); the panel draws them from the tool call's arguments as buttons and sends the picked label as the next message.
- **Context:** a message carries `[Nuzky]` lines with the selected clips and their range and the playhead, frozen at send time; "send the frame" asks the agent to look at the playhead with `inspect_frames` rather than attaching an image.
- **Tests:** `tests/e2e/fake_agent` stands in for `claude` (and as `fake_codex` for `codex`), refuses to run without the isolation flags, and edits through the real bridge (`scripts/repro.py ai_panel`, `ai_panel_codex`). The Codex parser's tests run on lines from real codex-cli 0.162.1 turns. The real Claude Code was checked once by hand on 8 Oct 2026 with Claude Code 2.1.292: it split a clip from the panel, the card named the split and the second message resumed the conversation. The real Codex 0.162.1 signed in with ChatGPT was checked the same way on 10 Oct 2026: asked to cut silences, it cut two pauses through Nuzky's tools, the card named them, its Undo restored the project and the next message resumed the conversation.
- **Not verified:** a plain Claude subscription login without a gateway (the machine it was built on uses one), Codex signed in with an API key rather than ChatGPT, macOS and Windows (the panel is off on Windows, where `--current` has no IPC yet). Anthropic's terms for a third-party app driving `claude -p` on a subscription: the Help Center (7 Oct 2026) names `claude -p` as usable with subscription limits, but ask Anthropic before a public release.
- Later: "Continue with ChatGPT" directly through OpenAI's open-source sign-in, then API keys, OpenRouter and Ollama.

## Phases

1. Headless foundation (done): `crates/session` and `crates/mcp` hosting their own session.
2. One authority: keyed undo steps in the engine, `keep_in_place`, `engine::speech`; `ProjectSession` on the live `Editor` with user edits, events, the writer thread and per-client access; the app on `Host` with its lock, read-only state and recovery dialog; one job system.
3. Transcripts per media file, `get_transcript`, `edit_transcript` and captions from the derived words, in the app and in MCP; the frontend's own transcript bookkeeping goes away.
4. IPC and the `nuzky-app mcp` bridge, then the run UI. Gate: Claude Code in a project folder cuts silences, adds captions and exports, live in the open app, with one Undo and a Stop mid-run.
5. Panel: `crates/agent` (direct CLIs, no ACP) and the dockable React panel, Claude Code first (done), then Codex. Gate: the same task from the panel through Claude Code and Codex, including Stop and Undo.
6. Direct ChatGPT sign-in and other providers.

## Risks

- Retiming after cuts is the hardest correctness problem; `map_words` needs fixtures with speed changes, detached audio, slivers, kept music, transitions and duplicated clips.
- Recognising a whole long recording once costs time up front; if that hurts, store which ranges a transcript covers.
- Blocking manual edits for a whole run may feel heavy; revisit after trying it by hand.
- On Windows the app is a GUI-subsystem executable; stdio for `nuzky-app mcp` must be tested there.
- Agent CLIs and subscription terms change; keep them behind `crates/agent`, recheck the flags on each new agent version, and keep the fail-closed checks.
- The agent's own isolation is its CLI's promise, not a sandbox; the fake agent proves Nuzky passes the flags, the real agent has to be rechecked by hand.
